# 可观测性与故障定位设计

## 可观察目标

设备停机时，现场人员不连电脑、不读流程代码，仅凭报警文案、三色状态灯和界面状态变量，在两分钟内定位到"哪个工位、哪一步、什么原因"；每个关键业务事件（进出站、抛料、重试耗尽、人工确认）都有可回查的记录。

## 适用边界

适用于所有整机程序的流程编写阶段（全流程平台与 PLC 主控-PC 代理形态均适用）。报警文案的界面呈现布局、日志系统的存储实现由平台与宿主负责，本块只管"流程里怎么埋点、怎么分层、怎么让故障可定位"。

## 当前事实与适配

跨项目一致的可观测性结构（四层）：

1. **报警分层与文案**：报警按"整机级（复位/通讯/气源）→ 工位级（某站物料/动作超时）→ 动作级（某指令失败）"分层组织；文案写"对象 + 现象 + 建议动作"（如"1#工作台 进料阻挡到位超时：检查物料是否卡阻挡"），不写"错误！""故障"这类无定位信息的文案。
2. **状态灯常驻映射**：三色灯（运行绿/暂停黄/报警红）由常驻监听流程统一维护，映射设备模式与报警状态；业务流程只翻转模式/报警变量，不直接写灯 IO——灯态在任何时刻都反映整机真实状态，而不是某个流程的局部视角。
3. **关键状态挂界面**：工位状态机变量、握手信号、关键计数呈现在界面（HMI 变量），运行时任意时刻可见每个工位处于九态中的哪一态、每个握手信号当前电平。
4. **业务事件落记录**：进出站绑定、抛料、重试耗尽、人工确认等事件按 data-struct.design 的载体决策落记录（变量/数据结构/本地文件），带时间与身份键，供事后回查与追溯对账。

故障定位路径与上面四层一一对应：报警文案给出工位与现象 → 界面状态变量给出该工位九态 → 握手信号给出上下游责任方 → 记录载体给出事件时序。流程设计时保证这条链路每一环都存在，而不是故障发生后靠读代码补。

## 参考阶段

1. 报警规划：列出整机报警清单，按三级分层编号，逐条写"对象+现象+建议动作"文案。
2. 状态灯映射：确定模式与报警变量到三色灯的映射表，由常驻监听流程统一执行。
3. 状态暴露：盘点所有跨流程状态变量（见 variables.design），标记需要挂界面的子集。
4. 埋点：在关键事件点（进出站、抛料、重试耗尽、人工确认）布置记录写入，与业务载体一致。
5. 空跑验证：空跑/验证流程走通的同时，确认每个典型故障场景都能沿"报警 → 状态 → 握手 → 记录"链路定位。

## 完成证据

制造一个典型故障（拔传感器/断料/握手失败），现场人员沿"报警文案 → 工位状态 → 握手信号 → 事件记录"在两分钟内定位原因；三色灯在运行、暂停、报警三种整机状态下均正确。

## 失败、超时与恢复

同一故障连环触发时按边沿/去抖处理，避免报警风暴淹没现场判断；可观测性埋点只写记录与呈现，不得改变流程状态、安全停止或基础报警行为（辅助诊断与主控职责分离）；记录载体写入失败按数据设计块的降级路径处理，不阻断工艺主流程。

## 反模式

- **报警文案无对象**：所有故障都报"设备故障"，现场只能逐个机构排查。文案写对象+现象+建议动作。
- **灯 IO 散装写**：各流程自己写状态灯，灯色反映的是流程局部视角而不是整机状态。灯由常驻监听统一映射。
- **关键状态只在内存**：工位状态/握手信号不挂界面，故障时只能连电脑看流程。跨流程状态进入界面呈现。
- **埋点改变业务**：为了记录事件顺手改了流程状态或顺序，观测侵入了控制。埋点只写记录。
- **报警风暴无去重**：同一故障每轮询周期报一次，现场把真报警淹没。边沿/去重触发。

## 幂等与甄别结论

记录写入与状态灯映射均为幂等赋值；报警触发按边沿语义，重复条件不重复报。历史项目"报警忽略""自动处理"分支、无文案的默认报警处理、按工位逐份复制且名称雷同无法区分的监控流程不吸收；三级报警分层、状态灯常驻映射、界面状态暴露、事件记录埋点被保留。
