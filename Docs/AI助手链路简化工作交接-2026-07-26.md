## 1. 本轮目标与结论

本轮原目标是评估 Automation AI 助手在小模型、有限上下文下的工具选择和 MCP 上下文膨胀问题。讨论后决定先以“降低复杂度、保证任务执行准确度”为优先，不引入新的动态路由架构。

当前决定：

- 用户只保留 `Diagnostic` 和 `Editor` 两种模式，不增加更多可见模式。
- 模式是权限边界，不再设计任务阶段工具包、动态工具列表或动态 Schema。
- `Editor` 是 `Diagnostic` 的完整超集，再增加编辑、运行和提交能力。
- 保留完整 ChangeSet V2、强类型 DTO、完整 `preview_change_set` Schema、Bridge 严格校验和 `preview → confirm → apply`。
- 暂不迁移 CLI，不实现动态 kind 裁剪、Contract Scope、Schema epoch 或每任务 MCP 实例。
- 优先删除重复提示、重复返回、旧兼容分支和无职责状态。

当前 MCP 自检结果：

- Editor Profile：66 个工具。
- `preview_change_set` 参数 Schema：48,462 字节。

## 6. 下一步优化方向

按优先顺序：

### 6.1 先收集真实任务数据

先运行约 30–50 个真实或上述标准任务，统计：

- 首次工具选择成功率。
- 首次 preview 成功率。
- 平均工具调用次数。
- 参数生成失败率。
- MCP 业务错误分类。
- 单工具返回字节数和整任务上下文增长。

没有数据前不要继续重构模式或工具路由。

### 6.2 压缩最大的工具返回

从日志中找返回最大的前五个工具，删除重复字段或改为已有分页。优先观察：

- `get_native_operation_schemas`
- `get_process_design_guide`
- `get_snapshot`
- `diagnose_issue/diagnose_proc`
- `apply_change_set`

不要统一增加 `detailLevel`、能力包或新元工具；只有实际返回确实过大时再修改具体工具。

### 6.3 静态压缩 preview Schema

如果真实测试证明 48KB Schema 仍影响模型：

- 缩短 DTO 中重复、说明性过强的字段描述。
- 继续提取公共 `$defs`。
- 结构约束留在 preview Schema，运行语义留在 semantic/native contract 和 behavior。
- 保留完整 action/kind 判别联合。

仍不建议动态 kind 裁剪。

### 6.4 MCP 工具目录只生成一次

当前 Dynamic Registry 初始化时会为 Editor、Diagnostic、RuntimeDiagnostic、FullPermission 多次反射并生成工具 Schema。可以评估：

```text
一次生成完整工具目录
→ 各 Profile 只按权威名称集合过滤
```

目标是减少启动工作和重复生成路径，不改变模型看到的契约。

### 6.5 清理其他兼容分支

先从实际 ACP 日志确认使用情况，再删除 `GooseAcpClient` 中零命中的旧格式兼容解析。不要按文件大小拆分类；只删除已经没有生产来源的分支。

## 7. 明确暂缓事项

除非人工测试给出明确证据，否则暂不实施：

- 新增用户模式。
- 按任务动态工具集合。
- LLM 任务路由器或 capability request 元工具。
- 动态 Schema/action/kind 裁剪。
- Contract Scope、Schema epoch。
- 每任务独立 MCP 实例。
- 为减少上下文而迁移 CLI。
- 拆分 ChangeSet V2 写入链。
