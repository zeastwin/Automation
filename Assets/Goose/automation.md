# Automation 平台路由

## 任务入口

- 用户只要求“设计、方案、结构或怎么写”而没有明确要求落入当前配置时，这是方案任务：平台经验会实质影响方案时按目标调用 `get_process_design_guide`，通常只选一个主主题；事实充分时可基于明确假设直接给出方案。不要加载写入 Skill、枚举当前项目资源或发起预演。
- 只读检查、审查、比较或解释现有 `Proc → Step → OperationType` 时，加载 `automation-process-review` Skill。
- 用户明确要求创建、修改、重构、复制或写入当前配置时，加载 `automation-process-authoring` Skill，并走 ChangeSet V2。
- 有明确运行症状时使用 `diagnose_issue` 获取运行现场证据；不要用静态配置检查替代实际运行证据。
- Automation 源码开发按目标调用 `get_platform_development_context`：HMI 使用 `hmi`，平台 API 使用 `platform-api`，自定义函数使用 `custom-function`；目标不明确时读取 `catalog`。

## 事实边界

- 只有答案或写入确实依赖当前对象时才读取资源；流程目标依赖现场资源而用户未给出精确对象时，优先直接采用设计指南 `goalCoverage.resourceRequests` 调用 `list_authoring_resources`，再根据真实工站、轴、点位、IO 或通讯资源决定下一步，不预猜名称。目录返回 `resourceRef` 时直接复制到支持该引用的字段，不转述或翻译展示名称；绑定失败采用错误结果中的同类型候选。
- 目录条目证明资源及其配置字段存在，但资源名称本身不自动证明气缸方向、安全位或业务角色；多个对象的角色仍无法确定时不得静默选择。
- 已发现的相关资源缺少点位、精确目标、极性或终态反馈时，这是证据缺口，不是该功能无需实现的证据。改用其他机构会改变用户目标含义时，询问用户或用 `config.placeholder` 保留原目标；单个输入未激活不证明相反机械终态。
- 运动工站已有实际轴但缺少目标点位时，先按用户目标规划有业务含义的点位名并在运动指令中使用；流程确认提交后可切到 `ResourceEdit` 用 `plan_motion_points` 登记名称。规划点位允许流程以 `incomplete` 保存，但人工示教坐标前不能运行；不要猜坐标，也不要把整段已知运动降级成占位。
- `step.disabled`、`operation.disabled` 必须如实保留，但禁用本身不自动等于 Bug；覆盖性检查遵循评审 Skill 的分页与原始 finding 规则。
- 配置事实、推断和未知信息分别陈述；方案中的假设不是当前项目事实。
- 控制流可达、业务条件可成立、资源可运行和现场已观测是不同证据层级，不互相替代。
- 占位只证明对应动作或结果仍未决；写在占位 `message` 里的重试、超时、清理和出口不是已实现结构，完成判断必须看工具返回的机械证据。

字段结构以 MCP Schema 为准，运行语义以 behavior/Guide 为准，当前配置与资源以 Bridge/Store 返回为准，启动条件以 Readiness 为准；Readiness 通过只证明结构满足当前保存/启动条件，不证明用户目标已完整实现。`get_process_design_guide` 是唯一的按需流程设计知识入口，功能块必须适配当前事实。不要在常驻上下文中复制这些动态契约。

项目中存在候选或可复用资源不代表必须使用；只绑定实现用户目标所必需且证据充分的对象，不为利用现有资源而追加用户目标之外的绑定。标准工艺时序中的复位、反馈验证和安全过渡属于实现用户目标本身，不是额外副作用。`resolve_operation_capability` 的 exact 只证明动作类型和契约已确定，不证明意图文字里的资源已经绑定。工具返回结构化 `issues` 时按当前修复包整体处理；有新证据或 `safeToRetry=true` 时可以继续修正，不用删减业务结构或探针预演猜平台规则。具体创建、评审和修改步骤由对应 Skill 提供。

取放类工艺的标准时序是：机构动作（夹持/释放）→ 反馈验证 → 复位或安全过渡 → 轴运动；输出保持激活时执行轴运动会收到预演警告。机构动作与轴运动的先后顺序缺少明确工艺事实时，按机构常识实现并在答复中标注假设；两种解读机械后果相反（如先复位再移动防撞击 vs 夹持随行移载）时先询问用户。
